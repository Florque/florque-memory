# florque-memory

**A structured knowledge layer for agents and apps.**

florque-memory stores what agents learn as a typed graph. You choose a **LinkML** ontology that
defines the classes, fields and relationships allowed. Every write is validated against it, so the
data stays structured and trustworthy even when many agents and sessions write to it over time.

It is more than agent memory. It is a shared data layer with two kinds of users:

- **Agents (today).** Each ontology becomes an [Agent Skill](#install-a-skill). Agents can search
  and load context safely, and they can create and update records safely. An invalid write is
  rejected with the reasons and changes nothing, so the agent fixes it and retries.
- **Apps (planned for the next iteration).** Deterministic, UI-based applications will read and
  write the same graph under the same ontology rules, so people and agents work on one source of truth.

Nothing is hard-coded: change the ontology, and the skill, validation and agent guide all follow.
By default the data lives in [Ladybug](https://github.com/LadybugDB/ladybug), an embedded graph
database stored in one file with no server. [Neo4j](#neo4j-backend) is optional.

A memory can hold one ontology, or a **project**: a work ontology (plans, goals, what is done) and a
domain ontology (systems, components, findings) in one graph, linked by [bridges](#project-mode-work--domain-in-one-memory).

> The Python package and CLI are named `memory-engine`.

## Install a skill

You only need one command. Prerequisite: [uv](https://docs.astral.sh/uv/).

```sh
git clone <this repo> florque-memory && cd florque-memory

scripts/install-skill.sh                                # bundled workgraph ontology -> workgraph-memory, for Claude Code
scripts/install-skill.sh family_tree                    # another bundled ontology -> family-tree-memory
scripts/install-skill.sh ./my_ontology.yaml claude pi   # your own ontology, for Claude Code and Pi
scripts/install-skill.sh --project payments.yaml        # a project: work + domain ontologies in one skill
```

`scripts/install-skill.sh [--reinstall-cli] [ONTOLOGY | --project MANIFEST] [TARGET ...]` does three things:

1. **Installs the CLI once, globally.** If `memory-engine` is not on `PATH`, it runs
   `uv tool install --editable <this repo>`. Every skill then shares one `mem`, and that `mem`
   tracks this checkout. `--reinstall-cli` forces a reinstall.
2. **Generates the skill** into `<data dir>/skills/<name>-memory/`:

   ```
   SKILL.md                    frontmatter + workflow, commands and example writes for this ontology
   references/ontology.md      the full ontology guide
   references/ontology.yaml    a copy of the ontology, so the skill is self-contained
   scripts/mem                 wrapper that pins the skill's ontology, then runs memory-engine
   ```

   A project skill holds `references/project.yaml`, `work.yaml` and `domain.yaml` instead of
   `ontology.yaml`, and its SKILL.md has a "Work and domain" section listing the bridges.

   Templates render everything from the YAML. Nothing is written by hand or generated by an LLM.
   The example writes in SKILL.md come from the ontology's required fields and edges, and tests
   check that they are valid.
3. **Symlinks** the skill into each target: `claude` (`~/.claude/skills`), `pi`
   (`~/.pi/agent/skills`) or any directory. The default target is `claude`.

`ONTOLOGY` is a `.yaml`/`.yml` path or the name of a [bundled ontology](#bundled-ontologies)
(default `workgraph`). After you edit the YAML or the manifest, run the script again. It regenerates
the skill in place and the links stay valid. You can install as many skills as you like, side by side.
Each one has [its own database](#where-the-data-lives), so they never see each other's data.

Start a new Claude Code session (or reload skills) to pick up a newly installed skill.

## Use it from Claude

You talk to Claude normally, and the skill tells it how to use the graph. Before writing, it reads
the ontology and searches for existing records, so it updates them instead of creating duplicates.
New records start as `proposed` until someone accepts them.

### With a bundled ontology

With `workgraph-memory` installed:

> What projects are currently in the workgraph?

> Add a project for the florque-memory app, with two objectives: reliable skills and MCP-based install.

> Plan an initiative for LLM evals of the generated skills. Break it into epics and tasks.

> Which work items are still open? Group them by initiative.

> Log a bug under the eval harness epic: runs leak into the real database when MEMORY_DATA_DIR is unset.

With `family-tree-memory` installed:

> Record that Ivan Petrov was born in 1902 in Tula, son of Pyotr and Anna. Source: Tula metric book 1902, entry 114.

> What do we know about Ivan Petrov's parents, and what is still unproven?

### With a custom ontology

Describe your domain and let Claude draft the ontology:

> Create a LinkML ontology for tracking customer orders, products and suppliers. Follow the
> conventions of the ontologies in `ontologies/`: `use_when` / `not_for` annotations on every
> class, and only the supported LinkML subset from the README. Save it as `orders_linkml.yaml`.

Then install it, and start using it in a new session:

```sh
scripts/install-skill.sh ./orders_linkml.yaml
```

> Add supplier Bloomfield Farms and link the tulip products they supply.

If the YAML uses something the engine does not support, the install fails with a list of issues.
Paste them back to Claude to fix. Tips for a good ontology:

- Give every class `use_when` / `not_for` annotations. They steer agents toward the right class.
- Set a schema-level `annotations: {skill_description: "..."}` to replace the generated skill description.
- Stay within the [supported LinkML subset](#supported-linkml-subset).

## Project mode: work + domain in one memory

A project combines two ontologies in one graph and one database:

- a **work** ontology (default `workgraph`): projects, goals, initiatives, epics, tasks, documents,
  signals, actors;
- a **domain** ontology you choose, for example `architecture`: systems, components, data entities,
  decisions, findings.

It is defined by a small manifest that only references the two ontologies:

```yaml
# payments.yaml
name: payments-platform
work: workgraph        # optional, default workgraph
domain: architecture   # required
domain_prefix: dom     # optional, default dom
db: ./memory/payments.lbdb   # optional: keep the graph next to the project (default: the data dir)
```

```sh
mem --project payments.yaml describe           # one guide for both modules
mem --project payments.yaml db-path            # database file and the identity it is stamped with
memory-engine skill build-project payments.yaml
```

- **Namespacing.** Domain names get the prefix, so there are no clashes: `Component` is
  `dom_Component`. A bare name still works when it is unambiguous.
- **Bridges.** Domain classes declare the roles they play (`bridge_role: component`). Work edges
  declare the role they target (`target_role: component`). The engine connects them at merge time.
  Bridges are optional. The bundled ontologies provide `scope`, `targets`, `addresses`, `changes`,
  `implements` and `measures`.

Full details, examples and limits: [docs/guides/project-mode.md](docs/guides/project-mode.md).

## Bundled ontologies

`ontologies/` collects ready-to-use ontologies. Where possible they are aligned with open
standards, so the data maps to existing tools. You can use each one by name, and each becomes a
`<name>-memory` skill.

| Name | Skill | What it models | Based on |
|---|---|---|---|
| `workgraph` | `workgraph-memory` | Program management: project, objectives / key results, initiatives → epics → tasks, documents, signals, actors | OKRs + agile work breakdown |
| `architecture` | `architecture-memory` | Software architecture for healthchecks and improvement planning: systems, components, interactions, data, quality objectives, decisions, findings, improvements. It is the domain side of a project | Minimal, domain-agnostic model |
| `family_tree` | `family-tree-memory` | Genealogy: trees, people, families, life events, nested historical places, sources with citation quality; claims stay `proposed` until a source confirms them | [GEDCOM 7](https://gedcom.io/specifications/FamilySearchGEDCOMv7.html) (INDI, FAM, EVEN, PLAC, SOUR, PEDI, QUAY) |

To add one:

1. Put `<name>_linkml.yaml` in `ontologies/`.
2. Cite the standard it follows in `see_also` and in the description.
3. Give every class `use_when` / `not_for` annotations.
4. To make it usable in a project, tag its classes with `bridge_role` where they match the bridge roles
   (`system`, `component`, `finding`, `decision`, `data`).

`tests/integration/test_bundled_ontologies.py` picks the new ontology up automatically. It must
load, build a skill and accept its own generated examples on Ladybug.

## Where the data lives

- **One database file per ontology or project.** The default path is `<data dir>/<name>.lbdb`, for
  example `workgraph.lbdb` or `payments-platform.lbdb`. Each skill is isolated, while all projects,
  agents and sessions that use the same ontology or project share one graph.
- **Project-local data.** A project's manifest can set `db`, so its graph lives next to the project
  instead of in the data dir. See [keep a project's data in the project](docs/guides/project-mode.md#keep-a-projects-data-in-the-project).
- **Identity.** Each file records which ontology or project it was created for. Opening it with a
  different domain, a different `domain_prefix`, or a different kind of memory is refused with
  `ontology_mismatch`, and nothing is written. See [docs/guides/database-identity.md](docs/guides/database-identity.md).
- **Data dir** (it also holds the generated skills):

  | OS | Data dir |
  |---|---|
  | macOS | `~/Library/Application Support/memory-engine/` |
  | Linux | `$XDG_DATA_HOME/memory-engine/` (default `~/.local/share/memory-engine/`) |
  | Windows | `%LOCALAPPDATA%\memory-engine\` |

- **Server / container.** Set `MEMORY_DATA_DIR` to persistent storage, such as
  `/var/lib/memory-engine` on a mounted volume. Never use the container's ephemeral filesystem.
  To back up, copy the files while no process has them open.
- **Concurrency.** Only one process at a time can open a file read-write. A command that finds the
  file locked retries for up to 5 seconds, then fails with `"error": "database_busy"`. That is
  enough for several agents on one machine. For many writers or several machines, use
  [Neo4j](#neo4j-backend).

## Viewing the graph

```sh
scripts/explore.sh family_tree          # → http://localhost:8000 (Ladybug Explorer)
scripts/explore.sh workgraph --port 8001 --live
docker stop memory-explorer-family-tree
```

The published `ghcr.io/ladybugdb/explorer` image lags behind and cannot open files written by
newer Ladybug versions ("different version… storage version"). So `explore.sh` builds Explorer
from its MIT source, with `@ladybugdb/core` pinned to the exact `ladybug` version memory-engine
uses (`mem db-path` reports it). The image is cached as `memory-engine/ladybug-explorer:<version>`.
The first build takes a few minutes, and after you upgrade `ladybug` the next run builds a new image.

By default it serves a **snapshot**, copied to `<data dir>/explorer/<name>/` while no process has
the database open, because the container cannot see Ladybug's file lock. Re-run it to refresh the
snapshot after new writes. `--live` serves the real file read-only instead. Don't write with `mem`
while it runs.

## Ontology reference

### How the ontology maps to the graph

- Each concrete class is a node label (Neo4j: plus a shared `:Node` label with a unique `id` constraint;
  Ladybug: a node table with `id` as primary key, and ids are kept unique across tables).
- Slots annotated `edge: true` are relationships, named in UPPER_SNAKE case (`part_of` → `PART_OF`).
  Their targets come from `range` or `slot_usage` `any_of`. Single-valued edges are replaced, not duplicated.
- `edge_properties: "role: Role (required)"` declares typed properties on an edge.
- The containment slot (`part_of`, or one annotated `containment: true`) forms a tree. Cycles are rejected.
- A class's required enum attribute (e.g. `WorkItem.kind`) is its *discriminator*. Annotations on its
  values add constraints: `allowed_parent: "WorkItem:epic,WorkItem:initiative"` and `requires: "serves"`.
- `rules` with `equals_string` preconditions and `required: true` postconditions are enforced.
- Bridges: a class's `bridge_role` annotation and a work edge's `target_role` (see [project mode](#project-mode-work--domain-in-one-memory)).

### Supported LinkML subset

Schema `id/name/title/description/prefixes/default_range/imports (linkml:types only)/annotations`;
classes `is_a/abstract/slots/attributes/slot_usage/rules/annotations`;
slots `identifier/required/range/any_of/multivalued/annotations`;
enums with `permissible_values` and annotations;
types `string, integer, float, double, decimal, boolean, date, datetime, uri, uriorcurie, curie, ncname`.
Anything else is rejected at load time rather than silently ignored.

Load-time checks also catch:

- unknown ranges and slots;
- `is_a` cycles;
- inconsistent `allowed_parent` references;
- **circular requirements**: classes whose required edges can only be satisfied by classes that can
  never be created themselves;
- unknown bridge roles, and bridges that are required (bridges must be optional).

## Advanced: direct CLI and programmatic use

Agents use the CLI through each skill's `scripts/mem` wrapper. You rarely need to call it yourself.
The sections below cover debugging, scripting and integration. Component-level documentation is in
[docs/README.md](docs/README.md).

### Configuration

| Variable | CLI option | Default |
|---|---|---|
| `MEMORY_BACKEND` | `--backend` | `ladybug` (or `neo4j`) |
| `MEMORY_DATA_DIR` | | per-user data dir (see [above](#where-the-data-lives)); holds the databases and generated skills |
| `MEMORY_DB_PATH` | `--db PATH` | `<data dir>/<name>.lbdb`; `:memory:` for a throwaway graph |
| `MEMORY_ONTOLOGY` | `--ontology PATH\|NAME` | bundled `workgraph` (a skill's `scripts/mem` pins its own) |
| `MEMORY_PROJECT` | `--project PATH` | unset; a project manifest. Replaces `MEMORY_ONTOLOGY` |
| `MEMORY_ACTOR` | | unset; when set, written to `created_by` / `updated_by` |
| `NEO4J_URI` | | `bolt://localhost:7687` |
| `NEO4J_USER` / `NEO4J_PASSWORD` | | `neo4j` / `memory-engine-dev` |
| `NEO4J_DATABASE` | | server default |

CLI options take precedence over environment variables. Set `MEMORY_DB_PATH` (or `--db`) for a
one-off separate graph, for example per client or per experiment. `--ontology` and `--project`
cannot be used together.

### Direct CLI

```sh
uv sync
uv run mem describe              # what the bundled workgraph ontology allows
uv run mem remember Project -p id=florque -p title=Florque -p summary="Flower shop platform."
uv run mem context florque
uv run memory-engine skill build path/to/ontology.yaml   # build a skill without linking it
uv run memory-engine skill build-project payments.yaml   # build a project skill
```

```sh
mem remember WorkItem -j '{"title":"Add payment step","summary":"Wizard step to connect payouts.",
                           "kind":"task","part_of":"init-wizard","depends_on":["task-auth"]}'
```

- Writes upsert by `id`. If `id` is omitted, one is generated (`workitem-1a2b3c4d`).
- Edge slots in the payload replace that slot's edges, and omitted edge slots are kept.
  `link` / `unlink` edit one edge.
- New nodes default to `status: proposed` when the ontology has that status. `null` clears an
  optional property.
- Rejected writes change nothing. On updates, only *new* violations block the write. Violations
  that already existed are reported by `mem validate`.
- Exit codes: `0` success, `1` the request was rejected, `2` the database is unusable
  (`database_busy`, `database_unavailable`, `ontology_mismatch`).

`mem tools` lists the tool names and their arguments, and `mem call <tool> '<json>'` invokes any of them.

### Programmatic use

```python
from memory_engine import OntologyEngine, load_ontology
from memory_engine.database.ladybug_driver import LadybugDriver
from memory_engine.tools import handle_agent_call

ontology = load_ontology("ontologies/workgraph_linkml.yaml")
engine = OntologyEngine(ontology, LadybugDriver("memory.lbdb", ontology.identifier))
engine.init()                    # create the tables
handle_agent_call(engine, "get_context", {"id": "init-wizard"})
# Neo4j: Neo4jDynamicDriver("bolt://localhost:7687", ("neo4j", "memory-engine-dev"))
```

A project is loaded the same way: `from memory_engine.core.project import load_project`, then
`load_project("payments.yaml")` returns the merged ontology.

### Neo4j backend

```sh
uv sync --extra neo4j            # or: pip install 'memory-engine[neo4j]'
docker compose up -d             # Neo4j 5 on bolt://localhost:7687 (neo4j / memory-engine-dev)
export MEMORY_BACKEND=neo4j
uv run mem init                  # constraints + indexes
```

### Ladybug schema and migrations

The database is one file plus a transient `.wal`. The CLI opens it for each command and creates or
migrates the tables on open, so you never need `mem init`. Running it anyway does no harm.
Two ontologies must not share a file, because their tables would clash; the identity stamp now
refuses that (see [database identity](docs/guides/database-identity.md)). Ladybug cannot share one
file across hosts or network filesystems.

Ladybug is schema-first. Each concrete class becomes a node table with typed columns, and each
edge slot becomes a rel table whose FROM/TO pairs are the class pairs the ontology allows
(`core/schema.py`). When the ontology grows (new classes, slots, edge targets or edge properties),
the change is applied the next time the database is opened. A slot's type change (e.g. string →
integer) cannot be migrated in place, and the error says so.

### Layout

```
ontologies/                predefined ontologies, bundled into the wheel (workgraph_linkml.yaml → `workgraph`)
scripts/install-skill.sh   build a skill from an ontology or project and link it into agents
scripts/explore.sh         serve a database in Ladybug Explorer
docs/                      component documentation (start at docs/README.md)
src/memory_engine/
  config.py           settings, data dir, bundled ontology lookup, project manifests
  cli.py              `memory-engine` / `mem`
  tools.py            tool registry + handle_agent_call (JSON in, JSON envelope out)
  core/parser.py      LinkML subset → Ontology model, load-time validation, bridge roles
  core/project.py     work + domain ontologies → one merged ontology (prefixing, bridge expansion)
  core/identity.py    identity stamp: what a database was created for, and the refusal
  core/casting.py     loose input (CLI strings, LLM JSON) → declared types
  core/engine.py      OntologyEngine: validated upserts, links, recall, context, validate
  core/guide.py       ontology → agent-facing markdown / JSON
  core/schema.py      ontology → GraphSchema (node/rel tables and typed columns)
  core/skill.py       ontology or project → Agent Skill (SKILL.md, references, scripts/mem)
  core/errors.py      error types and codes
  database/           GraphDriver protocol, open_driver factory,
                      LadybugDriver (embedded, default), Neo4jDynamicDriver (server)
```

### Tests

```sh
uv run pytest                     # unit + Ladybug + driver contract; Neo4j tests skip when it is down
docker compose up -d && uv run pytest tests/integration   # adds the Neo4j runs
```

`tests/integration/test_driver_contract.py` runs the same `GraphDriver` contract against the
in-memory fake, Ladybug and Neo4j, so the backends stay interchangeable. Tests never touch your
real graph or skills, because `MEMORY_DATA_DIR` points at a temp dir for every test.
